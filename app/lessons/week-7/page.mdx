## 이번 주에 할 일

Week 6까지 앱이 "일단은 돌아가는" 상태예요. 이번 주는 **정말 잘 돌아가는지 검증**합니다.

**테스트 = 미리 문제를 찾아내는 것.** 프로덕트가 실사용자 앞에 놓이기 전에 여러분이 먼저 잡아야 합니다.

### 결과물

- **QA 체크리스트** (30개 이상 항목)
- **Lighthouse 리포트** 스크린샷
- **실사용자 3명** 피드백
- **개선 커밋** (문제 최소 5개 해결)

## Part 1. QA - 4가지 관점

QA(Quality Assurance)는 크게 4가지 관점으로 검증합니다.

| 관점 | 뭐 보나 |
|---|---|
| **기능** | 스펙대로 작동하는가? |
| **호환성** | 다양한 브라우저·기기에서 되는가? |
| **성능** | 빠른가? |
| **접근성** | 시각·청각 장애인, 노약자도 쓸 수 있는가? |

각 관점의 체크리스트를 만들어 하나씩 확인합니다.

## Part 2. 기능 QA 체크리스트

여러분 앱의 **모든 사용자 시나리오**를 다 돌려보세요.

### 자소서 첨삭 앱 예시

```
[홈 페이지]
[ ] 로고 클릭 시 홈으로 이동
[ ] 헤더 메뉴 4개 모두 작동 (홈·입력·지난·설정)
[ ] "시작하기" CTA 버튼 → /edit으로 이동
[ ] 특징 카드 3개 모두 표시
[ ] 푸터 링크 클릭 가능

[/edit - 자소서 입력]
[ ] 회사명 필드 - 최소 2자 검증
[ ] 직무 필드 - 최소 2자 검증
[ ] 자소서 textarea - 최소 300자 검증
[ ] 글자 수 실시간 표시 (색깔 변화)
[ ] 검증 미통과 시 오류 메시지 표시
[ ] 검증 통과 후 제출 → localStorage에 저장 확인
[ ] 제출 후 /result?id=xxx로 이동
[ ] 브라우저 뒤로가기 → /edit로 돌아옴 (입력값 유지 or 초기화 명확)

[/result - 첨삭 결과]
[ ] URL의 id로 자소서 정보 정확히 표시
[ ] 존재하지 않는 id로 접속 시 안내 페이지
[ ] 최초 방문 시 자동 AI 첨삭 시작
[ ] 스트리밍 중 로딩 표시
[ ] 첨삭 완료 후 3개 섹션 표시 (구조·임팩트·적합성)
[ ] 마크다운이 실제로 렌더링됨 (heading, bold, list)
[ ] 완료 후 localStorage에 결과 캐시됨
[ ] 재방문 시 캐시된 결과 즉시 표시
[ ] "다시 첨삭받기" 버튼 - 캐시 무시하고 재요청

[/history - 지난 자소서]
[ ] 저장된 자소서들 카드로 표시
[ ] 상태 배지 정확 (첨삭 대기/완료)
[ ] 시간 표시 형식 ("2일 전" 등)
[ ] 카드 클릭 시 /result?id=xxx로 이동
[ ] 삭제 버튼 - 확인 팝업 후 삭제
[ ] 빈 상태 - "아직 없어요" 안내 + CTA

[/settings]
[ ] 프로필 정보 표시
[ ] 알림 토글 작동
```

여러분 앱은 여러분만의 시나리오로 이런 체크리스트를 만드세요. **각 페이지 × 각 인터랙션**을 다 커버.

## Part 3. 호환성 QA - 브라우저·기기

### 브라우저 체크

같은 URL을 다음 브라우저에서 다 열어보세요.

- **Chrome** (Windows, Mac)
- **Safari** (Mac, iOS)
- **Edge** (Windows)
- **Firefox** (Windows, Mac)
- **Samsung Internet** (Android)

각 브라우저에서 홈 페이지 + 핵심 시나리오(첨삭받기) 실행. 다른 게 있으면 기록.

### 기기 체크

- **데스크톱** (1920×1080)
- **노트북** (1366×768)
- **태블릿** (768×1024, iPad 크기)
- **큰 폰** (Galaxy S24, 390×844)
- **작은 폰** (iPhone SE, 375×667)

Chrome 개발자 도구 → **Toggle Device Toolbar** (Ctrl+Shift+M)로 각 기기 크기 시뮬레이션.

### 반응형 브레이크포인트

```
< 640px  → 모바일 (카드 1열, 햄버거 메뉴)
< 768px  → 태블릿 세로 (카드 2열)
< 1024px → 태블릿 가로
>= 1024px → 데스크톱 (카드 3열, 풀 메뉴)
```

## Part 4. 성능 QA - Lighthouse

Lighthouse는 Google의 웹 성능 진단 도구. Chrome에 기본 내장.

### Lighthouse 실행

1. Chrome에서 배포된 URL 열기.
2. **F12** (개발자 도구) → **Lighthouse** 탭.
3. 다음 선택:
   - Mode: **Navigation (Default)**
   - Device: **Mobile** (모바일 기준이 더 엄격)
   - Categories: **Performance, Accessibility, Best Practices, SEO**
4. **"Analyze page load"** 클릭.
5. 30초~1분 대기.

### 점수 해석

- **90+** ✅ 우수
- **70~89** ⚠️ 개선 필요
- **< 70** ❌ 문제 있음

### 흔한 문제와 해결

**LCP (Largest Contentful Paint)가 느림**
```
가장 큰 요소(대개 히어로 이미지)가 늦게 뜸.
- 이미지 최적화: next/image 사용, WebP 형식
- 이미지 preload
- 히어로 요소를 첫 페인트에 포함되게 서버 렌더링
```

**CLS (Cumulative Layout Shift)가 높음**
```
페이지 로딩 중 요소들이 튀어오르며 배치가 바뀜.
- 이미지·비디오에 width/height 지정
- 폰트 로딩 시 fallback 설정
- 광고나 임베드에 자리 미리 확보
```

**Accessibility가 낮음**
```
- 이미지에 alt 속성 누락
- <label> 태그 없이 input만 있음
- 텍스트-배경 대비 부족
- 헤딩 계층 잘못됨 (h1→h3, h2 건너뜀)
```

### AI Studio Build에 개선 요청

```
Lighthouse 리포트에서 다음 문제가 지적됐어. 하나씩 수정해줘.

1. CLS 점수 0.28 (초록 기준은 0.1 이하):
   - 히어로 이미지에 명시적 width/height 추가
   - 폰트에 font-display: swap 설정
   
2. Accessibility 점수 84:
   - 모든 이미지에 의미 있는 alt 속성
   - 폼 input에 <label for="..."> 연결
   - 색상 대비 부족 요소 (회색 텍스트) 어둡게 조정

3. Best Practices 점수 92:
   - console.error 나는 곳 원인 파악해서 수정
   - 외부 링크에 rel="noopener noreferrer" 추가
```

## Part 5. 접근성 (Accessibility, a11y)

접근성은 **모든 사람이 여러분 앱을 쓸 수 있게** 하는 것.

- 시각장애인 (스크린 리더 사용자)
- 색맹·색약자
- 손이 불편한 사용자 (키보드만 사용)
- 나이 드신 분

### 접근성 체크리스트

```
[ ] 모든 이미지에 alt 속성 (장식용은 alt="")
[ ] 폼의 모든 input에 <label> 연결
[ ] 버튼과 링크에 명확한 텍스트 or aria-label
[ ] 헤딩 계층 정확 (h1 → h2 → h3, 건너뛰지 않음)
[ ] 텍스트-배경 대비 4.5:1 이상 (WCAG AA)
[ ] Tab 키만으로 모든 인터랙션 가능
[ ] Focus 표시가 명확 (outline 등)
[ ] Escape 키로 모달 닫힘
[ ] Enter로 폼 제출
[ ] 색깔만으로 정보 전달하지 않음 (예: 오류 상태는 색+아이콘+텍스트)
[ ] 애니메이션에 prefers-reduced-motion 대응
[ ] 페이지 언어 명시 (<html lang="ko">)
```

### 키보드 테스트

마우스 없이 Tab · Shift+Tab · Enter · Space · Escape · 화살표 키만으로 앱 전체를 사용해보세요.

- Tab으로 요소 순서대로 focus 이동되는가?
- Focus 표시가 명확한가?
- 모든 인터랙션이 키보드로 가능한가?

## Part 6. 실사용자 테스트

가장 강력한 QA는 **진짜 사용자가 쓰는 걸 지켜보는 것**.

### 3명 이상 모집

- 페르소나에 가까운 사람 우선.
- 여러분 앱을 처음 보는 사람.
- 친구·가족·스터디원 OK.

### 테스트 시나리오

각 참가자에게:

1. **URL만 알려주고** 화면을 지켜봅니다. (그 사람이 어떻게 반응하는지 관찰)
2. 처음 미션: "회사에 자소서 첨삭받는다고 상상하고 사용해보세요." (또는 여러분 앱의 핵심 사용법)
3. **말은 나중에 하지 마세요.** 관찰만.
4. 완료 후 5~10분 인터뷰:
   - "어디서 헤맸어요?"
   - "무슨 생각이 들었어요?"
   - "이 앱에 뭐가 더 있으면 좋을 것 같아요?"

### 관찰 기록

각 참가자마다 다음을 기록.

```
참가자: [이름/별명]
날짜:
디바이스: [노트북/폰]

관찰한 것:
- [헤맨 부분]
- [기대와 달랐던 부분]
- [반응이 좋았던 부분]

인터뷰 답변:
- 
- 

개선 아이디어:
- 
```

3명이면 대개 90% 이상의 UX 문제가 발견됩니다.

## Part 7. 개선 우선순위 정하기

QA에서 발견한 문제가 20개라면, 8주짜리 프로젝트에 다 못 고쳐요. **우선순위**를 정합시다.

### 4분면 분류

```
              심각도 (Severity)
          낮음                높음
     ┌──────────────┬──────────────┐
많음 │  ② 중요       │  ① 최우선   │
발생 ├──────────────┼──────────────┤
빈도 │  ④ 나중       │  ③ 계획      │
적음 │              │              │
     └──────────────┴──────────────┘
```

- **① 최우선**: 자주 발생하는 심각한 문제. **이번 주 반드시 수정**.
- **② 중요**: 자주 발생하지만 심각하지 않음. 다음 우선순위.
- **③ 계획**: 드물지만 심각. 시간 되면.
- **④ 나중**: 드물고 사소. 넘어감.

### 우선순위 표 예시

```
| # | 문제 | 심각도 | 빈도 | 우선순위 |
|---|------|--------|------|----------|
| 1 | 첨삭 스트리밍 중 스크롤이 뛰어감 | 중 | 항상 | ① 최우선 |
| 2 | 모바일에서 헤더 메뉴 겹침 | 중 | 항상 | ① 최우선 |
| 3 | 500자 넘는 자소서 저장 시 오류 | 심각 | 가끔 | ③ 계획 |
| 4 | 다크모드에서 텍스트 대비 부족 | 낮음 | 항상 | ② 중요 |
| 5 | Safari에서 폰트 다르게 뜸 | 낮음 | 특정 브라우저 | ④ 나중 |
```

## Part 8. 개선 커밋

우선순위 ①번 문제부터 AI Studio Build에 요청해서 수정.

```
QA에서 발견한 문제들을 다음 순서로 수정해줘. 
각 수정 후 확인용 프리뷰 알려주세요.

1. [최우선] 첨삭 스트리밍 중 스크롤 튀는 문제:
   - useEffect로 messages 변경 감지
   - scrollIntoView({ behavior: 'smooth' })로 부드럽게

2. [최우선] 모바일 헤더 메뉴 겹침:
   - 640px 이하에서 햄버거 메뉴
   - 클릭 시 우측 슬라이드 인 사이드바
   - 배경 오버레이 (어두운 반투명)

3. [중요] 다크모드 텍스트 대비:
   - --text-muted 색깔을 명시적으로 조정
   - Lighthouse에서 4.5:1 이상 나오게

...
```

수정된 앱을 다시 QA 체크리스트로 재검증.
